<title>ICM 构建环境与 Dockerfile 兼容性说明</title>

**目的：**依据已核验的构建条件、题包交付要求和明确的未知项，判断 Dockerfile 的兼容性风险，并准备可复现的构建材料。本稿不是 ICM 全平台的正式服务规格，也不保证任意题包可以直接构建成功。

**关键结论：**ICM 不是统一的 Ubuntu 22.04 环境，也不存在已确认的统一 glibc、Python 或 GCC 版本。容器内的系统发行版和基础库版本由 Dockerfile 的 FROM 与后续安装步骤决定；构建机内核、资源额度和网络限制属于另一组条件。

# 已确认的构建条件

下表中的“已核验”表示当前链路或具体构建实例中观察到的配置，不表示 ICM 所有仓库、区域和版本的统一能力。

| 项目 | 当前可提供的信息 | 外部专家如何判断 |
|-|-|-|
| 目标系统与架构 | 已核验构建目标为 linux/amd64，即 x86_64。 | 基础镜像、wheel、二进制和系统包必须支持该架构；不能直接交付仅支持 ARM 的文件。若题包要求其他架构，需单独确认接入方案。 |
| 构建后端 | ByteBuild + BuildKit，使用 dockerfile.v0 前端。具体 BuildKit 和 frontend 版本尚未确认。 | 使用标准 Dockerfile；特殊语法、扩展挂载和额外构建能力需要单独确认兼容性。 |
| 构建入口 | 已核验仓库采用 Git 构建上下文，入口为 ./Dockerfile。 | 交付完整构建目录，说明 Dockerfile 路径和构建上下文根目录。上传到内部仓库由平台侧完成，不要求专家取得内部仓库权限。 |
| 常用指令 | 日志已验证 FROM、RUN、COPY、COPY --chmod，以及用户和权限调整可执行。 | 不需要仅因使用这些普通指令而改写题包；这不代表所有扩展语法均已验证。 |
| Linux 发行版 | 由基础镜像决定，不统一限定 Ubuntu 22.04。 | 写明发行版、版本与代号，固定基础镜像 digest；多阶段构建需分别说明各阶段的镜像身份。  <br/>**禁止使用**ubuntu时间戳的快照相关依赖，比如 [snapshot.ubuntu.com/ubuntu/20261101T000000Z](http://snapshot.ubuntu.com/ubuntu/20261101T000000Z) |
| 基础库版本 | glibc 或 musl、libstdc++、OpenSSL 等由基础镜像及后续安装步骤决定。 | 核对二进制要求的 GLIBC\_\*、GLIBCXX\_\* 等 ABI。ABI 是程序与基础库之间的二进制兼容接口；Alpine 的 musl 环境不能直接当作 glibc 环境使用。 |
| Python、编译器与框架 | 没有已确认的统一版本。 | 提供 Python、GCC/Clang、PyTorch 等实际版本和依赖锁；wheel 必须匹配 Python ABI 与目标架构。 |
| 构建网络 | 已核验仓库开启构建网络代理；不等于所有公网地址都稳定可达，也不代表后续执行阶段具有同样网络条件。 | 列出全部下载域名、URL 和鉴权需求，不依赖个人 VPN、网页登录态或专家机器上的本地缓存。 |
| 内部依赖源 | 平台侧存在内部镜像源；不要求外部专家访问内部源，也不能保证内部源保留所有历史版本。 | 将下载地址做成可配置参数，或交付同版本、同哈希的离线依赖，由平台侧配置内部下载地址。 |
| 构建缓存 | 已核验仓库开启缓存，但缓存可能缺失或导入失败。 | 题包应能够从空缓存构建；缓存只能加速，不能成为构建正确性的前提。 |
| 构建产物 | Dockerfile 步骤完成后，还需要成功推送和发布镜像。 | registry 上传失败应由平台侧排查，不能直接认定为专家 Dockerfile 错误。镜像发布成功后才能进入后续运行验收。 |

## 换源时必须保持的兼容性

**换源只改变下载位置，不应改变环境身份。**例如 Ubuntu jammy 不能换成 Debian bookworm 的源；固定日期快照、包版本、签名和哈希也必须保留。显式 wheel、deb、GitHub 文件和模型下载地址需要分别适配，不能只修改默认 APT 或 PyPI 源。

外部专家可以使用自己可访问的公共来源完成本地验证，并提供下载清单、固定版本和校验和；平台侧负责将这些来源映射到实际可用的内部来源。内部源缺少原版本时，应报告缺失，不能静默安装最新版。

# 题包交付与适配要求

下表是建议明确给专家的交付和评审要求，不是声称 ICM 已实施了所有项目统一的硬限制。

| 条件 | 专家需要满足或提前说明的内容 |
|-|-|
| 构建上下文完整 | COPY/ADD 引用的本地文件必须包含在交付包里，并检查 .dockerignore；不能引用专家机器上的绝对路径或构建上下文外文件。额外命名上下文需要提前说明，不能默认由接入链路自动提供。 |
| 安装过程非交互 | 构建不得等待终端输入、网页登录、人工确认或服务启动后手动操作。 |
| 依赖可复现 | 固定依赖版本、基础镜像 digest、模型和数据 revision，以及校验和。离线包应包含完整依赖闭包，即直接依赖及其所需的间接依赖。 |
| 凭证处理 | 不把个人 token、密码或私钥写入 Dockerfile、题包或镜像层。需要构建 secret 时提前说明名称和用途，由平台侧评审配置；不要把凭证值作为公开交付内容。 |
| 特殊权限 | 如需 privileged、宿主机 Docker socket、设备挂载、内核模块、FUSE 或特殊 mount，必须提前申报，不能默认可用。镜像内使用 root 不等于拥有宿主机特权。 |
| GPU 构建依赖 | 不要默认构建阶段有 GPU。如安装脚本执行 nvidia-smi、实际 CUDA 运算，或按可见 GPU 自动选择编译架构，必须单独说明并验证。使用 CUDA 工具链编译与实际运行 GPU 运算是不同要求。 |
| Compose 与多容器 | 当前准备链路存在 Compose 适配限制；这不是“ICM 全平台禁止 Compose”的结论。依赖多服务的题包需单独评审，不能删除服务强行适配。 |
| 构建与运行分开验收 | GPU 驱动、H20/L20 资源、Landlock 和评分目录权限属于后续运行条件，不能作为统一的 ICM 构建参数。镜像构建成功不代表这些条件已满足。 |

**禁止以改变题目语义换取构建成功：**不得擅自升级依赖、删除锁文件、关闭 TLS/GPG/哈希检查、修改评分逻辑，或统一 chmod 777。权限故障应按具体文件、运行用户和读写需求修复；涉及环境或依赖身份变化时应单独评审。

# 专家预检查与验收材料

**本地预检查：**在安装了 Docker 与 Buildx 的环境中，指定目标平台 linux/amd64，关闭构建缓存，并保留详细构建日志，验证题包能否从完整交付上下文独立构建。**尝试做一次无缓存构建**：

```Plain Text
docker buildx build --platform linux/amd64 --no-cache --progress=plain --load -t task:check ./environment
```

**版本记录：**分别记录各构建阶段及最终镜像的 /etc/os-release、libc、libstdc++、Python、编译器和 CUDA 工具链版本。未安装或不适用的组件应写明“不适用”，不能填入猜测值。本地观察到的内核和 GPU 驱动不能作为 ICM 平台规格。

建议随题包提供以下验收材料：

- Dockerfile 路径、构建上下文根目录、各阶段基础镜像引用与 digest。
- 依赖锁、软件包和二进制版本、目标架构及 Python ABI；模型和数据的固定 revision、文件清单与校验和。
- 完整下载清单，包括域名、URL、下载用途和是否需要鉴权；离线制品的文件清单与哈希。
- 额外构建参数、命名上下文、secret、特殊权限及构建期 GPU 需求，不包含凭证值。
- 空缓存构建日志、耗时、可测得的峰值资源需求及最终镜像大小，并注明测量环境。

**验收边界：**本地构建通过只是预检查，最终仍需平台侧在实际 ICM 环境完成构建和发布，再分别验证镜像拉取启动、原任务执行、verifier 与评分。Dockerfile 步骤完成、ICM 镜像发布成功和任务评分通过是三个独立结论，不能互相替代。
